## Что у нас сейчас (замер 2026-11-16 20:45)

- `eval/tools/spawn_session.sh` открывает каждую роль отдельным окном Terminal (osascript). `lineage.py` пишет в запись
  линии id окна и tty; autoclose и retire закрывают окно по id; `lineage_guard.py` сверяет tty наследника с tty окна.
- Mac: 24 ГБ, 15 CPU, свободно 50 %. Интерактивных сессий 14, окон Terminal 16.
- 13 групп процессов чужих сессий — **3642 МБ RSS** (≈ 280 МБ на сессию вместе с MCP-детьми). Terminal.app — **59 МБ**.
  Docker Desktop: VM — **8192 МиБ и 15 CPU**, на стороне Mac — 380 МБ.
- Защита: memguard снимает сессии при нехватке памяти (реакция), `heavy-gate.sh` — один тяжёлый гейт на Mac,
  reaper (`lineage.py reap --auto`, launchd, раз в 30 мин). Пороги — `instances/_shared.json`: `mem_warn` 20,
  `mem_critical` 10. **Пропуска на запуск новой сессии нет.**

- Docker на Mac уже на пути каждой сессии: `ANTHROPIC_BASE_URL=http://127.0.0.1:8787` — это контейнер
  `headroom-default` (1024 МБ). В VM ещё база доски `t-boards-postgres-1` и стенд HR; все контейнеры вместе —
  3259 МБ (`docker stats`, 16.11). Перезапуск Docker Desktop — минута без API у всех сессий.

**Вывод.** Окна дешёвые: проблема окон — навигация, а не память. Память съедают число сессий, тяжёлые гейты
(`tsc` 3,3 ГБ) и VM Docker (до 8 ГБ).

## На что ложится в tAIBE

Слой процесса: `spawn_session.sh` и линии (где живёт сессия), `team_status.py` и Нерв (статус), очередь владельца
(«ждёт тебя»). Метрики: окон 16 → 1; время «найти сессию, которая ждёт меня»; пик памяти при запуске команды; доступ

от Keychain, launchd и сервисов на хосте и складывает все сессии в один лимит памяти VM. Docker остаётся для тестов.

## План

### PR 1 — пропуск на запуск (ветка `feature/agent-bridge`, готово)

`team_status.py gate` и вызов перед каждой ролью в `spawn_session.sh --launch`: свободно памяти < `system.mem_warn`
(метрика Нерва — `memory_pressure`, «System-wide memory free percentage») или сессий Claude на Mac ≥
`system.max_sessions` → роль и следующие не открываются, причина с цифрами — в итог. `SPAWN_GATE=off` — открыть всё
равно; `--handoff` и `--dry-run` не проверяются. `max_sessions` = 10 в `instances/_shared.json` (при VM Docker 8 ГБ;
12 — если VM ≤ 5 ГБ). Проверка 16.11: `пропуск закрыт: сессий Claude 16 ≥ max_sessions 10 · память 36 %`.

### PR 2 — tmux хозяин сессий

1. `spawn_session.sh --terminal tmux`; по умолчанию — `terminal` в `instances/_shared.json`. Один tmux-сервер
   (`tmux -L agents`, `exit-empty off`), сессия tmux на продукт, окно на роль, имя — `<роль> <карточка>`.
2. Окружение: сервер стартует с `env -i` и списком разрешённых переменных, `update-environment ""`; окно —
   `new-window -e` с тем же списком. Иначе `CLAUDECODE`, `TAIBE_LINEAGE`, `CLAUDE_CODE_SSE_PORT` первой сессии уходят
   во все окна.
3. Линии: в запись — `terminal: tmux`, `#{session_id}:#{window_id}`, tty панели (читать после `launcher_started`,
   пустой tty — отказ). `lineage.py host()` знает tmux; `decide`, `own_record`, `window_plan`, выбор `record
   --terminal` — ветка tmux. Перед каждым `kill-pane` — tty, pid пусковой оболочки и запись новее старта сервера; не
   совпало — не закрывать. Закрытие одно: `remain-on-exit off`, «панели нет» — успех.
4. Сервер упал → роли открываются снова (`--resume`); tmux не отвечает → `--terminal terminal`.
5. merge-guard: агентам запрещены `tmux send-keys`, `capture-pane`, `pipe-pane`, `run-shell`, `kill-*`,
   `respawn-pane`, `attach`, `source-file` (как `osascript`); разрешён только путь `spawn_session.sh`.
6. Вид для владельца: строка статуса — сначала окна «ждёт тебя» (значок, счётчик), одна клавиша — к следующему
   ждущему, `prefix w` — список, мышь. Источник «ждёт» — `team_status.py` (ввод в TUI) и открытые пункты очереди роли.
   `context-threshold.py` — текст «новое окно tmux».
7. Тесты: `test_spawn_session.py` (tmux, dry-run), `test_lineage*.py` (подставной tmux, повтор id панели после
   перезапуска сервера), `test_team_status.py`, тесты merge-guard.

Приёмка: роли — окнами одного tmux; `--status` как раньше; handoff закрывает панель предшественника; autoclose и reap
работают; «ждёт тебя» видно в строке статуса за ≤ 15 с; окно Terminal одно; RSS tmux — замер.
Уже открытые сессии остаются в своих окнах Terminal: процесс нельзя перенести на другой tty.

### Фаза 2 — браузер и телефон (`infra/agent-bridge`), по условию

Сначала — `tmux attach` по SSH через WireGuard из приложения на телефоне (Termius, Blink) и сводка «кто ждёт» в боте
очереди. Фаза 2 — только если владелец назовёт конкретный пробел этого пути.

- `ab-pty`: порт на darwin (sysctl/libproc вместо `/proc`); сессия = `tmux attach -t <окно>`, процессы остаются у
  tmux; без forwarder хуков — статус из `team_status.py`; слушает `127.0.0.1` или `wg0`; секрет JWT из файла; без
  `admin/admin`.
- `ab-front` — холст терминалов и мобильная клавиатура; `ab-back` — реестр хостов (Mac и сервер). На Mac без Docker:
  Go-бинарь, статика, `uv`.
- Не берём `claudes`: `--dangerously-skip-permissions` обходит merge-guard и хуки. Берём только
  `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` для веб-терминала.
- Приёмка порта: история при подключении — последние 64 КБ, остальное по запросу (`main.go:4499` шлёт всю историю
  одним кадром, до 80 МБ); история — кольцо ≤ 256 КБ байт на сессию (`maxScrollback = 10000` кусков, `main.go:167`);
  permessage-deflate; на телефоне открыт сокет только окна в фокусе; `ab-pty` < 50 МБ RSS при 12 сессиях; бандл
  `ab-front` ≤ 300 КБ gzip; процессы — через libproc/sysctl, без вызова `ps`/`lsof`.

### Фаза 3 — сервер (только подготовка, решение владельца 16.11)

`infra/agent-host/`: `install.sh` для Debian/Ubuntu — tmux, пользователь `agents` без доступа к `docker.sock` прода,
`agents.slice` (`MemoryHigh`, `MemoryMax`, `CPUQuota`, `TasksMax`), tmux-сервер внутри slice
(`systemd-run --user --slice=agents.slice`), `ab-pty` — systemd-сервис на `wg0`. Проверка — в Linux-контейнере.
Сервер выбирается позже.

Исходные значения (расчёт: 280 МБ на сессию, `tsc` 3,3 ГБ; проверить в контейнере):

| VPS | MemoryHigh | MemoryMax | MemorySwapMax | CPUQuota | TasksMax | max_sessions |
|---|---|---|---|---|---|---|
| 4 ГБ, 2 vCPU | 2.8G | 3.2G | 512M | 150% | 2048 | 8, тяжёлые гейты запрещены |
| 8 ГБ, 4 vCPU | 6G | 6.8G | 1G | 300% | 4096 | 12 и один гейт |

`OOMPolicy=continue`; детям сессий — `oom_score_adj` +500, чтобы OOM снимал `claude`/`tsc`, а не tmux-сервер.

## Риски и открытые вопросы

- Навигация в tmux непривычна: мышь включена, список окон в строке статуса, меню окон — `prefix w`.
- `max_sessions`: предложение — 12 (13 сессий = 3,6 ГБ; `tsc` 3,3 ГБ; VM Docker до 8 ГБ; система ≈ 5 ГБ).
- VM Docker 8 ГБ и 15 CPU — снизить до 4–6 ГБ и 6 CPU (решение владельца, настройка Docker Desktop).
- 123 worktree при пределе 10: уборка влитых — `wt_gc.py sweep`, только с разрешения владельца.
