## 2. От чего защищает разделение ключа, а от чего нет

- **Защищает от утечки ключа с машины:** ключ попал в лог, транскрипт, вставку в чат или модель. Сейчас такая утечка
  открывает все 3 продукта до отзыва ключа. Ключ агента открывает их на 24 ч.
- **Не защищает от локального процесса.** Хаб без auth, и любой процесс пользователя зовёт его на `127.0.0.1:3050`
  с любым срезом. Хук не читает ключ, но может позвать хаб. Пункт приёмки «хуки не видят ключ хаба» выполняется
  буквально и мало значит, пока у хаба нет auth. Auth хаба — отдельная задача (OPS-21), в эту спеку она не входит.

## 3. Варианты

Процесс t-boards в хабе один. Поэтому продукт для ключа агента может прийти только двумя путями: из вызова (B1) или из
отдельного процесса на продукт (B2). B2 по цене равен A.

| | A. Сервер на продукт | B1. Продукт из вызова | C. Список воркспейсов в ключе | D. Ротация и срок |
|---|---|---|---|---|
| Суть | В хабе `t-boards-hr`, `t-boards-taibe`, …, у каждого ключ с областью «один воркспейс». Срезы `?tags=boards-<продукт>` | Один процесс. Вызов несёт продукт (как сейчас `session`), ключ агента выпускается на пару «сессия, воркспейс» | `metadata.workspaceIds: [...]`: ключ хаба видит только нужные продукты | Новый ключ владельца со сроком, отзыв старого, процедура ротации с откатом |
| Утечка ключа агента | 1 продукт | 1 продукт, 24 ч | продукты из списка | 3 продукта, 24 ч |
| Утечка ключа хаба | 1 продукт на ключ | 3 продукта | продукты из списка | 3 продукта до срока |
| Агент, который ошибся или выполняет чужую инструкцию | 1 продукт (свой срез) | без защиты: продукт в вызове пишет сам агент | продукты из списка | 3 продукта |
| Код | issuer: ключ с областью выпускает агента с той же областью; mirror — одно членство; маршруты вне `WORKSPACE_RESOLVED_PREFIXES` (`scoped-api-key-routes.ts:7-28`) ключу с областью закрыты — `list_notifications`, `ssr_*`, `whoami` дают 403, их надо открыть или скрыть | issuer и mirror как в A; MCP — продукт в каждом инструменте и кэш ключей по паре | парсер области и 31 проверка области в 9 файлах API | нет |
| Миграция | Имена инструментов (`t-boards-taibe_1mcp_*`): 11 файлов в двух репо, записи клиентов с `?tags=` | Новый параметр в 60 инструментах | Нет | Нет |
| Ресурсы | 3 процесса `node` вместо 1. Сессия на два продукта получает два среза: +27 тыс. токенов схем на запрос у клиентов, которые шлют все схемы (Continue на GLM). Claude Code грузит схемы по требованию | +1 параметр в схеме каждого инструмента | Без изменений | Без изменений |

**Предел всех вариантов, пока у хаба нет auth (OPS-21):** локальный процесс зовёт любой срез хаба, то есть любой
процесс t-boards. A защищает от утечки ключа с машины и от агента, который сам не выбирает срез. Локальный процесс
A не останавливает.

## 4. Рекомендация

**D закрывает TB-77, разделение по продуктам — после auth хаба** (владелец выбрал B: D со сроком ключа 90 дней, §5).
D выполняет приёмку карточки: новый ключ во всех
клиентах, старый отозван, хуки ключ хаба не берут. A до OPS-21 стоит переименования 11 файлов и трёх процессов, а от
локального процесса не защищает. B1 отклонён: продукт в вызове задаёт сам агент, поэтому защиты от агента нет, а от
утечки ключа хаба B1 не помогает. C отклонён: 31 проверка области ради одного воркспейса (вопрос 2).

**D — шаги владельца (окончательные, пункт очереди с откатом в `after`):**

1. t-boards → Настройки → API-ключи: новый ключ со сроком 90 дней (вариант B). Старый ключ не трогать. Окно с новым
   ключом не закрывать до конца шага 4: t-boards показывает значение ключа один раз (`settings:apiKey.createdModal`).
2. `security add-generic-password -U -s hr-helper-mcp -a T_BOARDS_API_KEY -w` — ключ спросит сам. Шаг заменяет
   старое значение в Keychain; его копии нигде нет, и откату оно не нужно (см. «Откат»).
3. `bash infra/scripts/dev-ai/mcp-hub.sh restart hub` (из основной папки tAIBE): только агрегатор, за секунды.
4. Проверка в Claude Code и в одном клиенте без отложенных инструментов (Continue): `whoami` — новый ключ,
   `list_workspaces` — 3 воркспейса. Если `whoami` отвечает старым ключом, процесс t-boards не перезапустился:
   `bash infra/scripts/dev-ai/mcp-hub.sh restart` (весь хаб, около минуты) и снова проверка. Если ключ нужен
   `apply-plan.mjs`:
   `T_BOARDS_API_KEY="$(bash infra/scripts/dev-ai/mcp-secret.sh T_BOARDS_API_KEY)" node boards/deploy/vps/seed/apply-plan.mjs`
   без `--apply` — план читается. Ключ берётся из Keychain и в историю shell не попадает.
5. Удаление старого ключа в настройках t-boards (удаление и есть отзыв). Проверка: в списке API-ключей его больше
   нет, `whoami` через хаб по-прежнему отвечает (новый ключ). Запрос старым ключом не нужен: его значения уже нигде нет.
6. В календарь — ротация через 85 дней по тем же шагам (за 5 дней до конца срока). Пропущенная ротация видна так:
   ключ истёк, и каждый инструмент t-boards во всех клиентах отвечает 401. Починка — шаги 1–4, старый ключ уже не
   действует.

Ключи агентов, выпущенные старым ключом, живут до 24 ч после шага 5: у них свой срок (`agent-limits.ts:3`). При
плановой ротации это не важно. При утечке — после шага 5 отключить агентов в t-boards (отключение отзывает все их
ключи) и включить снова. Проверка: в списке агентов (`GET /api/agent-identity`) у них нет живых ключей. Пока агент
отключён, мост на 401 сразу просит новый ключ агента, API отказывает, и каждый вызов открытой сессии падает с ошибкой
«agent key for <сессия>: …» (`boards/packages/mcp/src/kaneo/client.ts:67-71`). Отказ мост не запоминает
(`kaneo/agent-keys.ts:34-37`): после повторного включения открытая сессия на следующем вызове сама получит ключ, уже
через новый ключ хаба; перезапуск не нужен. Повторное включение не теряет членства агента (проверено по коду):
отключение удаляет только ключи и сессии агента (`apps/api/src/agent-identity/set-agent-enabled.ts:49,54`), а каждый
выпуск ключа сверяет членства агента с членствами владельца (`issue-agent-key.ts:164-166`, `mirror-memberships.ts`).

**Откат:** старый ключ действует до шага 5, но клиенты берут ключ только из Keychain, поэтому откат не возвращает
старое значение, а чинит новое.

- Шаг 4 не прошёл, окно ключа открыто — повторить шаг 2 с тем же новым ключом (опечатка при вводе), затем шаги 3–4.
- Окно ключа уже закрыто — удалить неудачный новый ключ, выпустить ещё один (шаг 1), затем шаги 2–4.
- После шага 5 — то же: новый ключ (шаг 1) и шаги 2–4.

Ключ выпускается раньше, чем Keychain меняется. Если выпуск ключа на шаге 1 не работает, шаг 2 не выполняется,
и старый ключ остаётся в Keychain.

**Дальше, отдельными карточками:** auth хаба (OPS-21), затем A по замеру; TB-96 (`access=read` для ключей с
областью).
