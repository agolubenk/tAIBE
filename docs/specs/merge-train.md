## Что строим

### Ф1. CI, база и стопка перед `pr.quorum` (S)

- Поля `mergeable`, `mergeStateStatus`, `baseRefName` добавляются в тот же запрос `_gh_view`, что уже читает файлы и
  `statusCheckRollup` (`sources.py:53-61`). Смена базы видна в списке PR (`base.ref` в ответе `_gh_list`). Новых
  запросов нет.
- **CI головы.** `pr.quorum` уходит только при зелёном CI, при упавшем автору уходит `pr.ci_failed`. Сейчас упавший
  CI проходит в кворум (`quorum.py:122`) — это ошибка SE-86, её правит boards отдельно и до Ф1. 13–14.11 approve на
  #245 и #247 пришли раньше CI, поэтому в строке документа видно состояние CI головы.
- Если `mergeable = CONFLICTING`, автору уходит событие `pr.conflict` вместо `pr.quorum`.
- Если `baseRefName` — не ветка по умолчанию, PR стоит в стопке. Статус — «ждёт #N», `pr.quorum` не уходит.
- **База влита.** Репозиторий вливает squash (у `8f24e9082` один родитель). GitHub переводит PR на ветку по умолчанию,
  голова прежняя, но в диффе — коммиты базы. Нерв замечает смену `baseRefName` и шлёт автору `pr.rebase`. После rebase
  голова новая: вердикты прежней головы в документе помечены «старые», линзы переносят approve по правилу дельты.
- `UNKNOWN` (GitHub ещё считает): повтор на следующем проходе.

### Ф2. Документ релиза (M) — SE-59 п. 3

- Файл `eval/nerve/state/products/<slug>/release.json` — состояние, в git не идёт. Строка PR ≤ 200 Б, файл ≤ 4 КБ:
  ночью 13–14.11 в очереди Контроля стояло 15 PR, это около 3 КБ. Строка влитого или закрытого PR уходит после
  итога деплоя. Поле `version` растёт при каждой записи. Запись атомарная: временный файл и `os.replace`.
- Писатель один — Нерв. Другие роли пишут в документ только через команды Нерва:
  - `nerve.py release show [--if-version N]` — чтение; без изменения версии — пустой ответ;
  - `nerve.py release decide <PR> hold|first|skip|resume "<причина>"` — решения Контроля (роль 5);
  - `nerve.py release ready <PR> <sha>` — автор отмечает голову готовой к линзам (Ф4).
- Строка PR: номер, голова, вердикты на голове, CI головы, `mergeable`, «ждёт #N», решение Контроля, итог деплоя.
  Поле «после мёржа» — ссылка на раздел PR или id пункта владельца. Для tAIBE, где мёрж не деплоит, это шаги
  раскатки (#172: `install.sh` и `memory-agent.sh install` на Mac).
- `release decide` может выполнить любая сессия: все работают от одного пользователя ОС. Это не граница доступа.
  Ворота мёржа — merge-guard. Решение в документе подписано линией сессии.
- Порядок — по времени кворума, решения Контроля меняют его. Координатор порядок не пишет: сообщение «#A → #B»
  заменяет `decide … first`.
- Документ — кэш. Источник правды — GitHub и комментарии PR. Битый или пропавший файл Нерв собирает заново за
  один полный проход.

### Ф3. После мёржа: деплой и проба прода (M) — только где мёрж = деплой

- Блок `deploy` в `instances/<slug>.json`:
  - `workflow` (у HR — `deploy-contabo.yml`);
  - `probes` — путь и ожидаемые коды: `/api/v1/health/ready` → 200, `/` → 200 или 30x, `/login` → 200;
  - `timeout_min: 120`, `start_wait_min: 10`.
  - У tAIBE блока нет: мёрж в `board-agents` деплой не запускает, стенд d4dev выкатывает release вручную.
- После мёржа Нерв ищет прогон workflow для коммита мёржа. Опрос — раз в 60 с с ETag (ответ 304 не тратит лимит
  GitHub).
- `start_wait_min` проверяет, что прогон создан (`queued` или `pending`), а не начался. Нет прогона за это время —
  деплой не нужен (`paths-ignore`: документы, `.claude/**`). Итог «без деплоя».
- **Очередь деплоя HR.** `concurrency: deploy-contabo`, `cancel-in-progress: false` (`deploy-contabo.yml:53-55`): в
  группе идёт один прогон и ждёт один, новый отменяет прежний ждущий. Отменённый прогон — не красное, если позже
  прошёл прогон для коммита-потомка. Итог строки — «выкачен прогоном `<sha>`».
- `timeout_min` считается от старта прогона (`in_progress`), а не от мёржа: чужой прогон в очереди идёт до 90 мин. У
  job тот же предел — `timeout-minutes: 120` (`deploy-contabo.yml:64`).
- Прогон кончился — пробы. GET без редиректов, тайм-аут 10 с, ответ сверяется с ожидаемым кодом. До красного — 3
  попытки за 2 мин: edge может ещё отдавать старый контейнер. `/api/v1/health/ready` workflow уже проверяет сам
  (`deploy-contabo.yml:3`); снаружи это проба сети.
- Итог пишется в документ и уходит одним событием: зелёное — `coord` (digest), красное — `release` (nervous) с
  причиной.
- Прогон не кончился за `timeout_min` после старта — красное событие «деплой не кончился».

## Отказы

- **Нерв лежит.** Работает ручной путь как сейчас: Контроль смотрит `gh pr view`. Документ не используется.
- **GitHub отвечает ошибкой.** PR остаётся в прежнем статусе, повтор на следующем проходе. Это поведение
  `poll_github` (`_raise_fails`).
- **Две записи сразу.** Писатель один, команды `release decide/ready` кладут заявку в файл входа. Нерв применяет
  заявки по порядку в своём проходе.
- **Проба красная из-за сети Mac.** Событие говорит, какая проба и какой код. Решает Контроль, автоотката нет.

## Приёмка

Замер — тот же подсчёт по журналу Нерва, окно ≥ 5 ч с ≥ 5 влитыми PR, до и после.

1. Событий Контролю на влитый PR — ≤ 1 в медиане (сейчас 2,5, p90 8).
2. Ручных сообщений с порядком «#A → #B» — 0 (сейчас 12 за 5,2 ч).
3. CI, конфликт и стопка видны до `pr.quorum`. Тесты `unittest` на ответы `gh` из фикстур:
   - CI `pending` и `failure` при трёх approve — `pr.quorum` нет (тесты карточки SE-86);
   - `CONFLICTING` и `UNKNOWN`;
   - база — не ветка по умолчанию;
   - база сменилась после squash — событие `pr.rebase`, вердикты прежней головы помечены «старые».
4. HR: у каждого мёржа в документе есть итог: «деплой + 3 пробы», «выкачен прогоном `<sha>`» или «без деплоя». Тест на
   отменённый ждущий прогон и прогон-потомок. Ни одна роль не держит свой опрос деплоя.
5. Действий владельца на релиз не больше, чем сейчас. Если владелец выберет пакетное «да» — одно на пачку.
