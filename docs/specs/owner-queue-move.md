## 5. Рекомендация — вариант А

Причины: условие карточки «меняется только хранилище» выполняется буквально; клиенты не меняют ни строки; SQL
остаётся SQL (окно списка, дельта и `if_version` — те же запросы на другом диалекте); один переход на запрос.

### 5.1. Модель данных

- Схема `oq` в Postgres досок: `oq.docs`, `oq.events`, `oq.files`. Колонки — как в `schema-queue.ts`; `product` —
  текстовый slug, как сейчас. Схему создают миграции досок (`boards/apps/api/drizzle/`).
- Типы — как в SQLite: время — `bigint` в мс (не `timestamptz`), `data_json` — `text` (не `jsonb`: `jsonb`
  переставляет ключи, и хэши §5.4 и бюджет байтов списка разойдутся).
- `oq.events.id` — `bigint generated by default as identity` (не `always`: копия с готовым id должна вставляться).
- Копируются как есть: `version`, `created_at`, `updated_at`, `updated_by`, `oq_events.id` и `at`. На них держатся
  `if_version`, ETag списка и дельта `/changes`.
- Значения по умолчанию из БД не используются: время и id ставит один путь записи в консоли (§5.3). Иначе два
  хранилища запишут разное время, и история с хэшами разойдётся.
- `oq_tokens`, `oq_products` и прочие таблицы консоли (алерты, пользователи, Telegram) остаются в SQLite консоли.
  Соединений этих таблиц с `oq_docs` в SQL нет — видимость задаётся списком slug (проверено линзой backend).

### 5.2. Доступ, роли и сеть

| Роль БД | Права | Где создаётся |
|---|---|---|
| `oq_owner` (`NOLOGIN`) | владелец схемы `oq` и её таблиц | миграция досок |
| `oq_console` | `USAGE` на `oq`, `SELECT/INSERT/UPDATE/DELETE` на таблицы, `UPDATE` на последовательность событий; `public.*` не видит | миграция — роль `NOLOGIN` и права; пароль и `LOGIN` — шаг ранбука (c), секрет в git не попадает |
| `t_boards` (приложение досок) | только `SELECT` на `oq.*` — для страницы §5.6 | миграция |

- Писатель один — консоль. Приложение досок писать в `oq` не может по правам, а не только по коду. Тест (a) на своём
  Postgres: `t_boards` получает отказ на запись в `oq`, `oq_console` — на чтение `public.*`.
- Общая внутренняя сеть docker только для двух участников: консоль и Postgres досок. Порт наружу не публикуется.
- Консоль при старте сверяет колонки схемы `oq` со своими и не стартует при расхождении — это контракт двух
  репозиториев.
- Сайт досок по-прежнему закрыт WireGuard: владелец и бот ходят только в консоль.

### 5.3. Один путь записи, блокировка и режимы хранилища

1. Рефакторинг в SQLite без смены поведения: все пути записи (`writeDoc`, `deleteDoc`, `importDoc`,
   `product-change.ts`, `insertFile`, `logEvent`) идут через одну функцию. `logEvent` входит в ту же транзакцию.
   Функция ставит время и все значения по умолчанию сама. У сортировок по `updated_at` появляется второй ключ `id`
   (HR `list.ts:42,53`) — иначе порядок равных мс разный в двух хранилищах.
2. В Postgres каждая транзакция записи первым оператором берёт `pg_advisory_xact_lock(<константа oq>)`. Это та же
   семантика, что у SQLite сейчас: один писатель за раз. Без неё курсор `/changes` молча пропускает события, а
   `if_version`, захваты и потолок вложений становятся гонкой (линза backend, B1–B2). Нагрузка записи не растёт:
   SQLite и сейчас пишет последовательно.
3. Флаг режима `OQ_STORE`:

| Режим | Первичное хранилище (проверка `if_version` здесь) | Зеркало | Читает |
|---|---|---|---|
| `sqlite` | SQLite | — | SQLite (как сейчас) |
| `dual-sqlite` | SQLite | Postgres | SQLite |
| `dual-pg` | Postgres | SQLite | Postgres |
| `pg` | Postgres | — | Postgres; файл SQLite только для чтения |

- **Зеркало документов** — один воркер в процессе консоли. Он идёт по `oq_events` первичного хранилища за своим
  курсором и копирует текущее состояние ключа (строки нет — удаляет). Порядок сохраняется, повтор безопасен, сбой
  между записью и зеркалом запись не теряет. Курсор хранится.
- **Строки `oq_files`** событий не пишут — они копируются во второе хранилище в том же пути записи.
- Сбой зеркала не валит запрос: счётчик `oq_mirror_fail` и строка в журнал; сверка (§5.4) докопирует.
- Смена режима — через env и перезапуск консоли. Метка запуска курсора `/changes` живёт в процессе (HR
  `changes.ts:24`), поэтому каждый клиент дельты получит один 410 и перечитает список — это нормально.

### 5.4. Копия и сверка

- Команда `oq-cli` копирует SQLite → Postgres и обратно (для отката). Повторный запуск безопасен.
- Перед копией в режим `dual-pg` — `setval` последовательности событий на `max(id)`. Иначе первая запись с
  Postgres первичным получит 23505 → 500.
- Отчёт копии: число документов по коллекции и продукту; sha256 **сырых байтов** `data_json` каждого документа
  (каноникализация спрятала бы настоящее расхождение); диапазоны id событий (число и max); строки вложений по
  `(id, deleted_at, sha256)`. Цель — 0 расхождений.
- Сверка в окне: каждые 15 мин — документы, изменённые с прошлого прохода, и удаления по журналу событий; раз в
  сутки — полный проход. Расхождение — счётчик, строка в журнал и докопирование из первичного хранилища.
- **Перекос продукта** чинится до копии, через путь смены продукта консоли (22 строки `w-taibe-*` и пункты
  `-taibe-` с product `hr-helper`). Копия остаётся байт в байт. Есть ли у консоли смена продукта для `work`, а не
  только для `items` (`/items/:id/product`), — проверить в карточке (b); нет — добавить там же.

### 5.5. Вложения

- Метаданные (`oq.files`) — в Postgres вместе с документами.
- Байты: до режима `pg` остаются на томе консоли. Куда они переезжают (S3 досок или Postgres) — решает backend после
  замера: число файлов и суммарный размер тома (`du` по `OQ_FILES_DIR`). Режим `pg` без решения по байтам не
  включается.

### 5.6. Очередь на доске

- Страница «Очередь владельца» в досках, только чтение: коллекции, фильтр по продукту, «открытые/отвеченные»,
  история пункта. Читает схему `oq` напрямую (роль `t_boards`, только `SELECT`).
- Включается с режима `dual-pg`: в `sqlite` Postgres пуст, в `dual-sqlite` он — зеркало с отставанием.
- Вложения: до режима `pg` — только метаданные и ссылка «открыть в `/queue`» (контейнер досок до тома консоли не
  достаёт).
- Видна только владельцу — та же проверка, что у решений (`actor.kind === "owner-ui"`). Ключи агентов, `agent:*` и
  `session:*` получают 403: в пунктах бывают личные заметки владельца.
- Данные `oq` не попадают в поиск досок, блокнот и инструменты MCP — иначе ключ агента прочтёт заметку владельца
  через поиск.
- Выдача — серверный фильтр и страница по 50 пунктов, как окно списка консоли. Без окна 1317 пунктов и 1342 проверки
  с историей — мегабайты на слабом телефоне через 3G.
- Ответ на доске — только через TB-102 (заявки по карточкам), как сейчас (Q-2).

### 5.7. Доступность и восстановление

После режима `pg` единственный канал решений владельца для обоих продуктов (и прода Lavaeon) зависит от Postgres
досок.

| Что случилось | Что видят владелец и агенты | Сколько длится | Кто чинит |
|---|---|---|---|
| Postgres досок перезапускается | `/api/oq/v1` отвечает 503; `/queue` и бот показывают ошибку; `oq_*` у сессий падают, MCP возвращает ошибку | время перезапуска контейнера — замер (c) | release |
| Postgres досок потерян | то же, до восстановления | восстановление из дампа — замер (c) | release |

- Потеря данных (RPO) при общем дампе каждые 2 ч — до 2 ч решений владельца. Для очереди это много. Рекомендация:
  отдельный `pg_dump -n oq` каждые 15 мин (схема — мегабайты) → RPO до 15 мин. Размер и длительность дампа —
  замер (c); если дамп дольше 1 мин — архив WAL вместо частого дампа.
- Восстановление схемы `oq` из дампа проверяется на своём контейнере до фазы 4 (приёмка, п. 9).
- Файл SQLite после фазы 4 — архив только для чтения (Q-3): последняя страховка, если потерян и дамп.

## 7. Фазы, ворота и откат

**Ворота — одно правило для всех переходов:** ≥ 48 ч в текущей фазе с 0 расхождений сверки и 0 ответов 5xx на
`/api/oq/v1` от консоли, плюс «да» владельца. Любое расхождение или 5xx перезапускает отсчёт 48 ч и сдвигает фазу.
Тогда 27.11 заканчивается в фазе 3, а не 4 — по решению владельца 14.11 это допустимо: несделанное уходит в новый
план, очередь работает в текущем режиме без потерь.

| Фаза | Что | Ворота входа | Откат |
|---|---|---|---|
| 0 | миграция схемы `oq` и ролей в досках; сеть на VPS | «да» владельца на миграцию и деплой досок | миграция вниз: схема пустая, данных нет |
| 1 | консоль с одним путём записи, блокировкой и флагом; режим `sqlite` | «да» владельца на деплой консоли (мёрж = деплой) | прежний образ консоли |
| 2 | перекос продукта исправлен; копия SQLite → Postgres; режим `dual-sqlite` | отчёт копии: 0 расхождений; «да» владельца | режим `sqlite`; данные Postgres не нужны |
| 3 | `setval`; режим `dual-pg`; страница на доске включается | правило ворот | режим `dual-sqlite`: SQLite не отстаёт, потерь нет |
| 4 | режим `pg`; SQLite — только для чтения, в архив | правило ворот; решение по байтам вложений; восстановление `oq` из дампа проверено; «да» владельца (Q-3) | копия Postgres → SQLite той же командой, режим `dual-pg` |

Каждый откат один раз прогоняется на репетиции: копия прод-`ops.db` из резервной копии и Postgres в своём
контейнере (правило проекта — свой контейнер, не живой Postgres).

## 9. Приёмка

1. Число документов в Postgres по коллекции и продукту = числу в SQLite = `oq_list total` в момент копии; отчёт
   копии — 0 расхождений по sha256 сырых байтов `data_json`, диапазонам id событий и строкам вложений.
2. `oq_history` 20 случайных пунктов совпадает в обоих хранилищах.
3. В каждом режиме зелёный дымовой прогон: `oq_put`, `oq_patch` с устаревшей `if_version` (409), `oq_list` (окно,
   `brief`, `open_only`, `unread`), `oq_get`, `oq_history`, `oq_files`, дельта `/changes`.
4. Гонки (тест на своём Postgres): N параллельных `PUT` с одной `if_version` → ровно один 200, остальные 409;
   поллер `/changes` под параллельной записью — 0 пропущенных документов; две загрузки вложений на границе потолка —
   одна проходит.
5. В минуту каждого переключения режима — 0 ответов 5xx на `/api/oq/v1` (журнал консоли).
6. Сверка: 0 расхождений по правилу ворот (§7); `oq_mirror_fail` — 0 или докопировано за 1 ч.
7. Вывод `queue_focus.py` до и после переезда совпадает (diff); Нерв доставляет `owner.answer`.
8. Ресурсы (замер release, числа — в карточку (c)): p95 `GET /api/oq/v1/db/items` и `PUT` до и после — не хуже
   +20 %; память консоли — в пределе 512 МБ; рост базы досок — в МБ; размер и длительность дампа `oq`.
9. Восстановление схемы `oq` из дампа проверено на своём контейнере; RPO — не больше 15 мин.
10. Страница «Очередь владельца» показывает столько же пунктов, сколько `oq_list`; ключ агента получает 403; поиск
    досок, блокнот и MCP пунктов `oq` не находят.
11. Права: `t_boards` не пишет в `oq`; `oq_console` не читает `public.*`.
12. Строки `work/*` — со сроками (planStart, planEnd, basePlanEnd) и привязками к карточкам; покрыто п. 1.
