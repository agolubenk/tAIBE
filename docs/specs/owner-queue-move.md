## 5. Рекомендация — вариант А

Причины: условие карточки «меняется только хранилище» выполняется буквально; клиенты не меняют ни строки; SQL
остаётся SQL (окно списка, дельта и `if_version` — те же запросы на другом диалекте); один переход на запрос.

### 5.1. Модель данных

- Схема `oq` в Postgres досок: `oq.docs`, `oq.events`, `oq.files`. Колонки — как в `schema-queue.ts`; `product` —
  текстовый slug, как сейчас. Схему создают миграции досок (`boards/apps/api/drizzle/`).
- Типы — как в SQLite: время — `bigint` в мс (не `timestamptz`), `data_json` — `text` (не `jsonb`: `jsonb`
  переставляет ключи, и хэши §5.4 и бюджет байтов списка разойдутся).
- `oq.events.id` — `bigint generated by default as identity` (не `always`: копия с готовым id должна вставляться).
- Копируются как есть: `version`, `created_at`, `updated_at`, `updated_by`, `oq_events.id` и `at`. На них держатся
  `if_version`, ETag списка и дельта `/changes`.
- Значения по умолчанию из БД не используются: время и id ставит один путь записи в консоли (§5.3). Иначе два
  хранилища запишут разное время, и история с хэшами разойдётся.
- `oq_tokens`, `oq_products` и прочие таблицы консоли (алерты, пользователи, Telegram) остаются в SQLite консоли.
  Соединений этих таблиц с `oq_docs` в SQL нет — видимость задаётся списком slug (проверено линзой backend).

### 5.2. Доступ, роли и сеть

| Роль БД | Права | Где создаётся |
|---|---|---|
| `oq_owner` (`NOLOGIN`) | владелец схемы `oq` и её таблиц | миграция досок |
| `oq_console` | `USAGE` на `oq`, `SELECT/INSERT/UPDATE/DELETE` на таблицы, `UPDATE` на последовательность событий; `public.*` не видит | миграция — роль `NOLOGIN` и права; пароль и `LOGIN` — шаг ранбука (c), секрет в git не попадает |

- Писатель один — консоль. Приложение досок ходит в Postgres суперпользователем `t_boards` (§2), права его не
  ограничивают. Защита в три слоя:
  1. Доски не трогают `oq.*` вовсе: страница §5.6 читает через API консоли.
  2. Гейт в CI: в коде досок нет SQL к `oq.*`.
  3. Триггеры `BEFORE INSERT OR UPDATE OR DELETE` (и `TRUNCATE`) на таблицах `oq.*` отказывают, если
     `session_user <> 'oq_console'`. Обычные триггеры действуют и на суперпользователя — случайная запись из кода
     досок упадёт. Восстановление `oq` из дампа поэтому идёт с `pg_restore --disable-triggers`.
- Тесты (a) на своём Postgres: запись под `t_boards` получает отказ триггера; `oq_console` получает отказ на чтение
  `public.*`.
- Таймауты роли (b): `ALTER ROLE oq_console SET lock_timeout = '5s', statement_timeout = '10s',
  idle_in_transaction_session_timeout = '10s'`; пул консоли — не больше 4. Иначе одна зависшая транзакция с
  advisory-блокировкой (§5.3) останавливает все записи и выедает пул. `lock_timeout` действует и на
  `pg_advisory_xact_lock` (допущение по документации PostgreSQL 16, проверить тестом в (b)).
- Снять с приложения досок суперпользователя (новая роль входа, передача владения таблицами `public`) — отдельная
  карточка: миграция с «да» владельца и риском для всех досок, не до 27.11 (§10).
- Роли в Postgres общие на кластер, не на базу. Миграция создаёт роли через `DO … IF NOT EXISTS (SELECT FROM
  pg_roles …)`, иначе вторая база на том же кластере (интеграционные тесты, репетиция) падает на «role already
  exists».
- Сеть: у консоли и досок разные compose-проекты, поэтому общая сеть — только внешняя, `oq_net` (`--internal`), два
  участника: консоль и Postgres досок. Порт наружу не публикуется.
  - Сеть создаётся шагом ранбука фазы 0 до мёржа PR (b). Без неё `docker compose up` стека HR падает целиком, а там
    мёрж = деплой.
  - Подключение Postgres досок к сети пересоздаёт его контейнер: короткий простой досок, нужно окно и «да» на деплой
    досок (деплой ручной, `install.sh`).
  - Откат сети не нужен: пустая сеть безвредна.
- `pg_hba` (c): `t_boards` — только из `10.78.0.0/28` (сеть `tb`, `compose.yml:146`), `oq_console` — только из
  `oq_net`, остальное — `reject`. Консоль смотрит в интернет; если её взломают, она дотянется только до своей роли.
- Сверка колонок схемы `oq` при старте (контракт двух репозиториев) и отказ старта — только там, где Postgres
  первичный (`dual-pg`, `pg`). В `sqlite` консоль к Postgres не подключается вовсе. В `dual-sqlite` при расхождении
  колонок или недоступности Postgres зеркало выключается, растёт `oq_mirror_fail`, запросы обслуживает SQLite: сбой
  зеркала не останавливает очередь.
- Сайт досок по-прежнему закрыт WireGuard: владелец и бот ходят только в консоль.

### 5.3. Один путь записи, блокировка и режимы хранилища

1. Рефакторинг в SQLite без смены поведения: все пути записи (`writeDoc`, `deleteDoc`, `importDoc`,
   `product-change.ts`, `insertFile`, `logEvent`) идут через одну функцию. `logEvent` входит в ту же транзакцию.
   Функция ставит время и все значения по умолчанию сама. У сортировок по `updated_at` появляется второй ключ `id`
   (HR `list.ts:42,53`) — иначе порядок равных мс разный в двух хранилищах.
2. В Postgres каждая транзакция записи первым оператором берёт `pg_advisory_xact_lock(<константа oq>)`. Это та же
   семантика, что у SQLite сейчас: один писатель за раз. Без неё курсор `/changes` молча пропускает события, а
   `if_version`, захваты и потолок вложений становятся гонкой (линза backend, B1–B2). Нагрузка записи не растёт:
   SQLite и сейчас пишет последовательно.
3. Флаг режима `OQ_STORE`:

| Режим | Первичное хранилище (проверка `if_version` здесь) | Зеркало | Читает |
|---|---|---|---|
| `sqlite` | SQLite | — | SQLite (как сейчас) |
| `dual-sqlite` | SQLite | Postgres | SQLite |
| `dual-pg` | Postgres | SQLite | Postgres |
| `pg` | Postgres | — | Postgres; файл SQLite только для чтения |

- **Зеркало документов** — один воркер в процессе консоли. Он идёт по `oq_events` первичного хранилища за своим
  курсором, копирует саму строку события с тем же `id` и текущее состояние ключа (строки нет — удаляет). Порядок
  сохраняется, повтор безопасен, сбой между записью и зеркалом запись не теряет. Курсор хранится. Id событий в двух
  хранилищах совпадают — иначе после смены первичного вставка зеркала упрётся в первичный ключ.
- **Строки `oq_files`** событий не пишут — они копируются во второе хранилище в том же пути записи.
- Сбой зеркала не валит запрос: счётчик `oq_mirror_fail` и строка в журнал; сверка (§5.4) докопирует.
- **Смена режима** — через env и перезапуск, всегда по шагам:
  1. Стоп консоли.
  2. Догнать зеркало: курсор воркера = `max(id)` событий первичного хранилища.
  3. Сверка — 0 расхождений.
  4. Старт в новом режиме.
- Консоль не стартует первичной, если в её хранилище `max(id)` событий меньше, чем во втором: иначе откат 3 → 2
  потеряет хвост записей. Исключение — Postgres потерян (§5.7): принудительный старт флагом, шаг ранбука.
- Метка запуска курсора `/changes` живёт в процессе (HR `changes.ts:24`), поэтому каждый клиент дельты после смены
  режима получит один 410 и перечитает список — это нормально.
- Диалект (линза backend, N2): `octet_length` вместо `length(cast … as blob)`, API libsql `run`/`get`/`rowsAffected`
  против драйвера Postgres, `count`/`sum` и `bigint` приходят строкой → `Number()`. Список — чек-лист карточки (b).

### 5.4. Копия и сверка

- Команда `oq-cli` копирует SQLite → Postgres и обратно (для отката). Повторный запуск безопасен.
- `setval` последовательности событий на `max(id)` — при каждом старте консоли с Postgres первичным, под той же
  advisory-блокировкой, после шагов смены режима (§5.3). Без него первая запись с Postgres первичным получит
  23505 → 500.
- Отчёт копии: число документов по коллекции и продукту; sha256 **сырых байтов** `data_json` каждого документа
  (каноникализация спрятала бы настоящее расхождение); диапазоны id событий (число и max); строки вложений по
  `(id, deleted_at, sha256)`. Цель — 0 расхождений.
- Сверка в окне: каждые 15 мин — документы, изменённые с прошлого прохода, и удаления по журналу событий; раз в
  сутки — полный проход. Расхождение — счётчик, строка в журнал и докопирование из первичного хранилища.
- **Перекос продукта** чинится до копии, через путь смены продукта консоли (22 строки `w-taibe-*` и пункты
  `-taibe-` с product `hr-helper`). Копия остаётся байт в байт. Есть ли у консоли смена продукта для `work`, а не
  только для `items` (`/items/:id/product`), — проверить в карточке (b); нет — добавить там же.

### 5.5. Вложения

- Метаданные (`oq.files`) — в Postgres вместе с документами.
- Байты: до режима `pg` остаются на томе консоли. Куда они переезжают (S3 досок или Postgres) — решает backend после
  замера: число файлов и суммарный размер тома (`du` по `OQ_FILES_DIR`). Режим `pg` без решения по байтам не
  включается.

### 5.6. Очередь на доске

- Страница «Очередь владельца» в досках, только чтение: коллекции, фильтр по продукту, «открытые/отвеченные»,
  история пункта.
- Читает **через API консоли** — тем же `QueueClient`, что TB-102 и TB-108 (`get`, `history`; метод списка с окном —
  `listAll` из #155 или новый, в карточке (e)). Схему `oq` доски не читают: приложение досок — суперпользователь
  (§5.2), и прямое чтение держалось бы только на коде.
- Поэтому страница от режима хранилища не зависит: консоль отдаёт первичное хранилище в любом режиме, и п. 10
  приёмки («столько же, сколько `oq_list`») держится по построению.
- Токен досок в консоли должен видеть оба продукта (Q-1) — проверить в карточке (e).
- Вложения — только метаданные и ссылка «открыть в `/queue`».
- Видна только владельцу — та же проверка, что у решений (`actor.kind === "owner-ui"`). Ключи агентов, `agent:*` и
  `session:*` получают 403: в пунктах бывают личные заметки владельца.
- Данные `oq` доски не хранят и не индексируют — в поиск досок, блокнот и инструменты MCP они не попадают по
  построению. Приёмка п. 10 это проверяет.
- Выдача — фильтры и окно списка консоли, страница по 50 пунктов. Без окна 1317 пунктов и 1342 проверки с историей —
  мегабайты на слабом телефоне через 3G.
- Ответ на доске — только через TB-102 (заявки по карточкам), как сейчас (Q-2).

### 5.7. Доступность и восстановление

С фазы 3 (`dual-pg`) единственный канал решений владельца для обоих продуктов (и прода Lavaeon) зависит от Postgres
досок. В фазах 1–2 консоль от Postgres не зависит (§5.2).

| Что случилось | Что видят владелец и агенты | Сколько длится | Кто чинит |
|---|---|---|---|
| Postgres досок перезапускается | `/api/oq/v1` отвечает 503; `/queue` и бот показывают ошибку; `oq_*` у сессий падают, MCP возвращает ошибку | время перезапуска контейнера — замер (c) | release |
| Postgres потерян в фазе 3 | то же, пока консоль не перезапущена в `dual-sqlite` принудительным стартом (§5.3); потеря — отставание зеркала | минуты — шаг ранбука | release через пункт владельцу |
| Postgres потерян в фазе 4 | то же, до восстановления | восстановление из дампа — замер (c) | release через пункт владельцу |

- Потеря данных (RPO) при общем дампе каждые 2 ч — до 2 ч решений владельца. Для очереди это много. Рекомендация к
  фазе 4: отдельный `pg_dump -n oq` каждые 15 мин (схема — мегабайты) → RPO до 15 мин. В `backup.sh` один интервал
  (`TB_BACKUP_EVERY`) и хранение 3 дня (`backup.sh:9,27`) — нужен второй цикл со своим хранением, например 24 ч.
  Диск = размер дампа × 96 в сутки; размер и длительность — замер (c); если дамп дольше 1 мин — архив WAL.
- Память: у Postgres досок `mem_limit: 256m` (`compose.yml:17`). До фазы 2 release замеряет пик RSS под опросом
  очереди (бот, Нерв, сессии); пик выше 70 % — поднять до 512m после проверки RAM VPS. Убийство Postgres по OOM кладёт
  и доски, и очередь.
- Роли кластерные и в дамп не входят. Проверка восстановления досок (`mac/restore-check.sh:5,28`: `set -eu`,
  `pg_restore --no-owner` без `--no-privileges`) после фазы 0 упадёт на `GRANT … TO oq_console`. В карточке (a):
  скрипт создаёт роли до восстановления (или `--no-privileges`, затем права заново). То же — в ранбуке восстановления
  прода (`boards/deploy/vps/README.md:64-69`) и в проверке дампа `oq`; восстановление `oq` — с `--disable-triggers`
  (§5.2).
- Восстановление схемы `oq` из дампа проверяется на своём контейнере до фазы 4 (приёмка, п. 9).
- Файл SQLite после фазы 4 — архив только для чтения (Q-3): последняя страховка, если потерян и дамп.

## 9. Приёмка

1. Число документов в Postgres по коллекции и продукту = числу в SQLite = `oq_list total` в момент копии; отчёт
   копии — 0 расхождений по sha256 сырых байтов `data_json`, диапазонам id событий и строкам вложений.
2. `oq_history` 20 случайных пунктов совпадает в обоих хранилищах.
3. В каждом режиме зелёный дымовой прогон: `oq_put`, `oq_patch` с устаревшей `if_version` (409), `oq_list` (окно,
   `brief`, `open_only`, `unread`), `oq_get`, `oq_history`, `oq_files`, дельта `/changes`.
4. Гонки (тест на своём Postgres): N параллельных `PUT` с одной `if_version` → ровно один 200, остальные 409;
   поллер `/changes` под параллельной записью — 0 пропущенных документов; две загрузки вложений на границе потолка —
   одна проходит.
5. В минуту каждого переключения режима — 0 ответов 5xx на `/api/oq/v1` (журнал консоли).
6. Сверка: 0 расхождений по правилу ворот (§7); `oq_mirror_fail` — 0 или докопировано за 1 ч.
7. Вывод `queue_focus.py` до и после переезда совпадает (diff); Нерв доставляет `owner.answer`.
8. Ресурсы (замер release, числа — в карточку (c)): p95 `GET /api/oq/v1/db/items` и `PUT` — базовый снят до деплоя
   фазы 1 (иначе «до» уже измерит новый путь записи), после — не хуже +20 %; память консоли — в пределе 512 МБ; пик
   RSS Postgres досок — ниже 70 % лимита; рост базы досок — в МБ; размер и длительность дампа `oq`.
9. Восстановление схемы `oq` из дампа (`--disable-triggers`) проверено на своём контейнере; `restore-check.sh`
   зелёный после фазы 0; RPO — не больше 15 мин.
10. Страница «Очередь владельца» показывает столько же пунктов, сколько `oq_list`; ключ агента получает 403; поиск
    досок, блокнот и MCP пунктов `oq` не находят.
11. Защита записи: запись в `oq.*` под `t_boards` получает отказ триггера; в коде досок нет SQL к `oq.*` (гейт);
    `oq_console` не читает `public.*`.
12. Смена режима: откат 3 → 2 после записи в `dual-pg` — 0 потерянных событий; консоль с отстающим хранилищем
    первичной не стартует; в `dual-sqlite` с выключенным Postgres очередь отвечает, растёт `oq_mirror_fail`.
13. Строки `work/*` — со сроками (planStart, planEnd, basePlanEnd) и привязками к карточкам; покрыто п. 1.
